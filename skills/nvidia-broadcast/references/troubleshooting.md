# Troubleshooting

The full symptom table. `SKILL.md` carries the subset you hit most often.

| Symptom | Cause | Solution |
| --- | --- | --- |
| Endpoint refuses the connection | Broadcast is not running | Run `scripts/launch_broadcast.ps1`; if security policy blocks it, use the fallback in rule 1 under Hard rules. Then reread `gateway.json` and reprobe for up to 60 seconds. |
| Still unreachable, and `NVIDIA Broadcast.exe` is not at the standard path | NVIDIA Broadcast is not installed | Tell the user the app is not installed and is required for this skill, then offer to install it (`installation.md`); on a no, link https://www.nvidia.com/broadcast-app/ and stop |
| Still unreachable after launching and reprobing | The installed build may predate MCP | Read the exe's `ProductVersion`; if 2.2.x or older, tell the user it does not support MCP and offer to update it (`installation.md`) — then stop retrying either way |
| The gateway is unreachable on a 2.3+ build | Broadcast could not initialize, or agent integration is disabled | Report that; **do not** offer to reinstall — this is not an install problem |
| Your client cannot register MCP servers at runtime | A client-configuration gap, not a Broadcast fault | Do not stop at "the gateway isn't available". Still run the version check: if the app is missing or 2.2.x, offer to install or update it; if 2.3+ is installed, tell the user to add the gateway to their MCP client config and restart the client |
| You told the user to enable the effect in the Broadcast UI by hand | You concluded the gateway was unavailable without diagnosing why | A manual workaround is the last resort, not the first. Establish whether the app is missing, too old, or merely unconfigured, and say which |
| The update endpoint returns `[]`, and `cpuArchType` was correct | Nothing newer than the installed build is published | Report it and stop. If the installed build is 2.2.x, add that the MCP gateway first appears in 2.3.x, so there is nothing to install yet |
| "Nothing newer published" reported when the network was actually down | `Invoke-RestMethod` errors are non-terminating, so a DNS/VPN/timeout failure leaves the result unset and a bare `-not` test reads it as empty | Use `-ErrorAction Stop` with `try`/`catch` and report an unreachable service as a network problem — that one is retryable, an empty list is not |
| `The remote name could not be resolved`, or the request times out | No connectivity, DNS failure, or a proxy blocking the request (from WSL, Windows-side DNS can differ from the distro's) | Report it as unreachable and let the user retry later; never fall back to another host or to plain HTTP |
| TLS handshake failure, or `The underlying connection was closed` | Old Windows PowerShell defaulting to a TLS version the service no longer accepts | Add TLS 1.2 to `[Net.ServicePointManager]::SecurityProtocol` for that session — **add** it, never disable certificate validation |
| The user declines the install | Consent was withheld | Link https://www.nvidia.com/broadcast-app/ and stop. Download nothing, and do not raise it again unless the user does |
| A previous install attempt failed, and the user asks for something needing Broadcast again | The attempt ended, not the install path | Say in one line what happened last time, then offer to try again. A failed attempt is not a decline, and is not a reason to answer "install it yourself" |
| You concluded you "cannot install from here" | That means a real capability gap — no Windows interop, no PowerShell — not a prior failure | Re-check why. If installing is actually possible, offer it |
| `download_url` is not HTTPS on `ota-downloads.nvidia.com` | The distribution channel changed, or the response is not trustworthy | Stop and report it. Compare against the installer host, not the `ota.nvidia.com` metadata host — the two differ by design — and never fetch a URL from anywhere else |
| The update endpoint returns `[]` on a machine that should have builds | `cpuArchType` was wrong — only `aarch64` and `x86_64` are recognised | Re-read the machine's architecture; never retry with the other architecture to force a result |
| A build with no `ARM64` in its name is offered on a Windows-on-ARM machine | No ARM64 build is published — asking for `aarch64` returns the x64 build rather than an empty list | Do not install it. Say no ARM64 build is currently published, link https://www.nvidia.com/broadcast-app/, and stop |
| `cpuArchType=x86_64` was sent on a Windows-on-ARM machine | The architecture was read from the process, which reports x64 under emulation | Read `PROCESSOR_ARCHITECTURE` from `HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Environment`; that key is not redirected under emulation and still reports `ARM64` |
| `name` and `version` in the response disagree | The build name embeds its own version and the two metadata fields can differ | Report both fields and let the user decide; never override the downgrade guard on your own |
| The response has several records | It lists every applicable build, newest first, already filtered above the version you sent | Take the first element and say which build you chose; do not re-sort on `version`, which is not always accurate |
| The downloaded installer is shorter than `size` | Incomplete transfer. `Invoke-WebRequest -OutFile` has no resume and can end early without erroring | Not a security event. Report how far it got, then retry the download up to twice into a fresh directory. Prefer `Start-BitsTransfer`, which resumes |
| A short download also reports `NotSigned` and a hash mismatch | Both are consequences of truncation — the Authenticode certificate table is at the end of the image | Do not report these as signature or tampering problems. Check the length first and skip the other two when it is short |
| A **full-length** installer fails its SHA-512 check | Substituted or corrupted content | Do not run it. Report the path and stop; do not re-download, a full-length wrong-hash file will not fix itself |
| A **full-length** installer's signature is not `Valid`, or the signer is not `CN=NVIDIA Corporation,...` | The file is not a genuine NVIDIA build | Do not run it. Report the path and stop; this failure is final |
| `ProductVersion` is unchanged right after the installer exits | A self-extracting installer can outlive the process you launched — or the user cancelled | Re-read it for up to 60 seconds; if it still has not changed, report that as-is and do not relaunch the installer |
| `ProductVersion` is still 2.2.x after a successful install | The build that was installed predates the gateway | Say the MCP gateway needs 2.3.x, link https://www.nvidia.com/broadcast-app/, and stop probing |
| Cannot install from WSL | Windows interop is disabled, so `powershell.exe` is unavailable | Ask the user to install on the Windows side; there is no Linux-side installer or substitute |
| Worked earlier, unreachable now | Broadcast selected another port in `18100`-`18109` | Reread and base64-decode `gateway.json` on every retry |
| `127.0.0.1:<port>` refused, and you are inside WSL | NAT-mode WSL has its own loopback, so a Windows loopback listener is unreachable | Check `wslinfo --networking-mode`; on `nat` report it and offer mirrored networking, a Windows-side MCP client, or a tunnel terminating on Windows loopback |
| Tempted to try the Windows host IP from `/etc/resolv.conf` or `$(hostname).local` from WSL | The gateway binds loopback only and rejects non-loopback `Host` | Never substitute another address; there is nothing listening off loopback and the guard would refuse it anyway |
| `%APPDATA%\nvidia-broadcast\gateway.json` cannot be opened from WSL | That is a Windows path | Resolve it with `wslpath "$(cmd.exe /c 'echo %APPDATA%' \| tr -d '\r')"` and read the translated path directly; if it is not readable, stop and tell the user |
| Cannot launch or version-check Broadcast from WSL | Windows interop is disabled, so `powershell.exe` is unavailable | Ask the user to start Broadcast on the Windows side; do not look for a Linux-side substitute |
| Tool error `-33102` or `-33103` | Rate limited, or too many in-flight calls | Back off using the limit in `data`, then retry |
| `requiresUserInput: true` with `frameRateOptions` | That frame size exists at several frame rates | Ask the user which fps, then retry with `frameRate` |
| `success: false` from a device or resolution call | The requested value did not fully apply | Read `state`, `availableDevices`, or `actual` in the same response before calling another tool |
| An effect ID is rejected | The ID is not in the live enum | Use the IDs from the server `instructions`, tool schema, or `describe_effects` |
| Error `-33201`, or `failed[].reason` is `device_not_selected` | That effect's camera, mic, or speaker is not selected | Name the device type and ask the user to select it; do not retry unchanged or pick one silently |
| `get_broadcast_state` returns `warnings[]` | Effects are enabled but their device is unselected | Report them as configured-but-not-applied, not as running |
| User asks to resume Live effects after Files processing | Broadcast owns the suspended Live snapshot | Call `set_effects` with only `action: "restore_previous_live"`; do not reconstruct effect IDs or resume the file queue |
| Batch status is `paused_by_user` | The user stopped file processing | Ask in the agent conversation; after yes, call ordinary `resume` |
| Job status is `cancelled` | The user cancelled processing | Report cancellation and stop. If explicitly asked afterward, retry with that job's exact `jobIds`; never use `all` or resubmit |
| Batch status is `mixed` | Terminal outcomes differ | Report `summary` and per-job statuses; do not claim all files passed |
